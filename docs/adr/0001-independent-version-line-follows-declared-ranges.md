# 独立版本线包跟随依赖方声明，而非 npm 最新版

actdsh 要在上游某个 release 的依赖树之外，为没有发布过该 tag 版本的家族包（独立版本线包）选定一个版本装进安装包。我们决定：这个版本由依赖它的家族包所声明的区间决定，取满足全部声明的最高版；只有无声明可依的 peer 补齐包才由 actdsh 自行选版。这样构建版本清单记录的版本，就是运行时实际被加载的版本。

## Considered Options

**顶层装 npm 最新稳定版，允许子树嵌套旧版**（原实现）。被否：构建版本清单会原样进入面向用户的发布说明，而实际被依赖方加载的是嵌套副本。清单于是对外报告了一个没有任何代码在使用的版本。同时顶层那份最新包成为纯占体积的死重。

**全树收敛到单一版本**（给独立版本线包也加强制覆盖）。被否：这会把上游从未一起测试过的版本组合塞进安装包。`0.x` 线上的 minor 跳版可能破坏兼容，风险最终落在用户身上，而 actdsh 无法验证。

**跟随声明区间**（采纳）。清单诚实，不产生死重，且与上游自己的解析结果一致——这本就是钉死脚本一直声称的「最终树与严格模式自动安装结果等价」。

## Consequences

- 触发本次决策的具体事故：`dsh-office-to-pdf@0.1.7-alpha.2` 精确锁定 `libreoffice-kit@0.0.1`，而当时 npm 最新稳定版是 `0.1.0`。原实现装了 `0.1.0` 到顶层、`0.0.1` 嵌套，清单报告 `0.1.0`。
- 采纳后，独立版本线包的版本随上游声明漂移，不再随 npm 发版漂移。上游发布独立包的新版本本身不会再改变 actdsh 的产物。
- 需要一个能判断「某版本是否满足某声明区间」的能力。已观察到的声明形态只有精确版与 `~X.Y.Z`，但上游未来可能使用其他形态；支持范围应与实际需要相称，不做完整的 semver 实现。
- 校验闸门必须断言顶层副本。嵌套副本是包管理器的正常行为，把它当成纯度缺陷会持续产生误报——这正是本次事故的直接触发点。
